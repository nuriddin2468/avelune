# 0012. Package manager: pnpm 11

- Status: Accepted (2026-09-23, product-owner go-ahead)
- Date: 2026-09-23
- Related: 0001

## Context

pnpm lines as of 2026-09-23: 10.34.5 (last release 2026-07-10), **11.27.1** (2026-09-20) and 12.5.1 (12.0.0 released 2026-08-26). Nx 23.2.1's source contains explicit pnpm 11 handling and no references to pnpm 12. `@changesets/cli` 3 requires pnpm ≥ 10. The development machine has pnpm 10.26.1 from Homebrew.

## Decision

- Pin **`"packageManager": "pnpm@11.27.1"`** in the root `package.json`. pnpm's version management switches to the pinned version inside the repo, with no global change.
- Set `engines.pnpm` to `>=11.27.1 <12` so that other versions fail fast.
- Use `pnpm-workspace.yaml` for workspace packages, with `catalog:` entries for shared versions so that Angular, TypeScript and test-tool versions are declared once.
- The CI image uses the same pinned version via the `packageManager` field.

## Alternatives considered

- **pnpm 12:** newest, but Nx 23 doesn't yet reference it (lockfile parsing and pruning risk). Revisit when Nx lists support.
- **pnpm 10:** works, but that line's last release was in July; 11 is the actively maintained line that Nx handles explicitly.
- **npm / yarn:** weaker workspace isolation (phantom dependencies) and no catalogs. Rejected.

## Consequences

- Phase 1 verifies `nx graph`, `nx affected` and lockfile pruning with pnpm 11 before any other work.
- Upgrading pnpm is a dedicated merge request that updates this ADR's version line.

## Addendum: supply-chain settings (Phase 1, 2026-09-23)

Verified in Phase 1: `nx graph` parses the pnpm 11 lockfile (`lockfileVersion: '9.0'`, 906 external nodes); `nx affected` follows project files and global inputs (`tsconfig.base.json`, `nx.json`, `.browserslistrc`, `eslint.config.mjs`); Nx's lockfile pruning (`createLockFile`) produced a 154-line lockfile for `dist/packages/ui` that installs with `pnpm install --frozen-lockfile` under pnpm 11.27.1.

pnpm 11 changed two defaults that this repository keeps and states explicitly in `pnpm-workspace.yaml`:

- **`minimumReleaseAge: 1440`.** No version younger than 24 hours is resolved, including transitive ones. This is a guard against compromised releases and is not overridden per package (no `minimumReleaseAgeExclude`). Consequence: a release is adopted one day after publication at the earliest. On 2026-09-23 this held back `@angular/cdk` and `@angular/aria` 22.2.0, `ng-packagr` 22.2.0, `prettier` 3.9.9 and `@microsoft/api-extractor` 7.59.2; the previous releases are pinned instead (compatibility.md §2), and the upgrades are tracked in ROADMAP.md.
- **`allowBuilds`.** Install scripts are blocked unless listed. Only `esbuild` is allowed (it verifies its platform binary). `nx`, `lefthook`, `lmdb`, `msgpackr-extract` and `@parcel/watcher` are listed as `false`: their scripts only update the Nx Cloud client, install hooks (done by our `prepare` script), or build native code that already arrives prebuilt. A new dependency with an install script fails `pnpm install` until it is reviewed and listed.

pnpm 11 also reads no settings from `.npmrc` other than auth and registry; there is no `.npmrc` in the repository.
